# 현재 외부 변경 저장 정책 (0.10.6)

외부 변경 배너를 표시하지 않고 열린 문서의 내용을 유지합니다. 다음 저장 시 같은 파일에 현재 내용을 덮어쓰며 충돌 사본을 생성하지 않습니다. AppKit이 외부 수정으로 저장을 거부하면 같은 경로에 Save As 작업으로 재시도합니다. 저장 실패는 정상 오류로 전달합니다. 완료된 편집의 강제 종료 복구 기록은 유지합니다.

아래 0.8.0 기록의 양쪽 보존·충돌 사본 생성 정책은 0.10.6부터 일반 저장에 적용하지 않습니다.

# 강제 종료 복구와 외부 변경 충돌 (0.8.0)

## 동작

완료된 획, 삭제, 이동·크기 변경, 복사·붙여넣기, 이미지·도형, 용지 변경 및 Undo/Redo를 변경 기록에 남깁니다. 문서 전체를 매번 인코딩하는 대신 변경한 획만 체크섬을 붙여 기록하고 파일 동기화를 완료합니다. 문서가 열릴 때 기준 데이터도 별도로 보존합니다.

강제 종료 후에는 기준 데이터와 마지막 정상 기록까지 재생하여 **복구 노트 사본**을 만듭니다. 원본은 복구 과정에서 덮어쓰지 않습니다. 이미 실제 파일에 저장된 내용과 복구 결과가 같으면 중복 사본을 만들지 않습니다. 이전에 만든 복구 사본을 사용자가 편집했으면 재실행 시 그 사본을 덮어쓰지 않습니다. 실행 중인 다른 LightNote 문서의 기록은 파일 잠금으로 구분하여 복구하지 않습니다.

기록 끝이 잘렸거나 체크섬이 맞지 않으면 그 앞의 정상 기록까지 복구하고 손상 기록을 보존합니다. 기준 데이터 자체가 손상되었으면 복구했다고 표시하거나 원본 기록을 삭제하지 않습니다. 기록 저장에 실패하면 노트 상단에 오류를 표시합니다.

외부 프로그램이 수정한 파일과 미저장 로컬 편집이 충돌하면 외부 원본을 유지하고 현재 편집을 **충돌 노트 사본**으로 저장합니다. 안전한 쓰기 내부에서 늦게 감지한 외부 변경은 별도 사본으로 보존한 후 저장합니다. iCloud의 미해결 버전도 읽을 수 있으면 별도 보존하며, 임의로 해결 완료 처리하지 않습니다. 파일 경로가 바뀌면 복구 기록과 마지막 문서 참조도 함께 갱신합니다.

## 위치

- `~/Library/Application Support/LightNote/Notes`: 일반 노트 및 복구·충돌·외부 변경 사본
- `~/Library/Application Support/LightNote/Recovery`: 기준 데이터와 편집 기록; 손상된 꼬리 기록은 `.recovered` 폴더에 보존
- 노트 상단의 안내와 **폴더 열기** 버튼으로 위 폴더에 접근할 수 있습니다.

정상적인 창 닫기 시 기록을 정리합니다. 정상 종료 후 기록이 남았더라도 저장된 파일과 일치하면 다음 시작에서 사본을 추가하지 않습니다. 장시간 열린 세션의 기록은 종료 전까지 쌓이며, 현재는 중간 압축을 하지 않습니다.

## 검증

```sh
swift test
/Applications/LightNote.app/Contents/MacOS/LightNote --self-test
/Applications/LightNote.app/Contents/MacOS/LightNote --self-test --save-tests-only
python3 scripts/test-saving-lifecycle.py
python3 scripts/test-crash-recovery.py
```

모든 프로세스 검사는 격리한 임시 폴더와 합성 문서만 사용합니다. 강제 종료 검사는 직접 만든 자식 프로세스 PID에만 `SIGKILL`을 보냅니다.

- 저장 전 강제 종료 → 완료된 편집 복구
- 인코딩 중 강제 종료 → 편집 복구
- 임시 파일 쓰기 완료 후, 원본 교체 전 강제 종료 → 편집 복구
- 저장 완료 후 새 편집을 추가한 뒤 강제 종료 → 저장 이후 편집까지 복구
- 외부 파일이 바뀐 상태에서 강제 종료 → 외부 원본과 로컬 복구 사본 모두 보존
- 충돌 사본 저장 완료 후 강제 종료 → 저장한 사본을 중복 복구하지 않음
- 정상 닫기와 재실행 → 불필요한 복구 사본 없음
- 복구 후 다시 재실행 → 복구 중복 없음
- 필기·도형·이미지·이동·삭제·용지·Undo/Redo를 포함한 문서 전체 일치 확인
- 손상·잘린 기록, 손상된 기준 데이터, 누락·손상된 원본, 이미 편집한 복구 사본 및 실행 중 잠금 검사
- 외부 변경 알림이 미저장 편집을 버리지 않는지, 유효하지 않은 외부 파일의 원본 바이트도 보존하는지 확인
- 이전 자동 저장 순서·종료 취소·재시도 및 필기·이미지·도형 회귀 검사 유지

이 검사는 실제 프로세스 강제 종료와 로컬 파일 충돌을 검증합니다. **다른 기기와의 실제 iCloud 동기화는 별도 검증 대상**입니다. 전원 차단·저장 장치 고장까지 보장하지 않으며, 마우스를 떼기 전 진행 중인 획은 완료된 획과 같은 복구 보장 대상이 아닙니다. 복구 기록 저장 자체가 실패하면 상단 안내에 따라 노트를 저장해야 합니다. 대량 선택 편집은 해당 변경 데이터의 기록 비용이 추가됩니다.

참고: [Apple 파일 변경 알림](https://developer.apple.com/documentation/foundation/nsfilepresenter/presenteditemdidchange()), [NSDocument의 파일 조정](https://developer.apple.com/library/archive/documentation/General/Devpedia-CocoaApp-MOSX/DocArchitecture.html).


## 배포판 회귀 결과

0.8.0 universal 배포판의 arm64 실행에서 코어 24개, 기존 네이티브 검사, 비동기 저장·외부 변경 검사, 실제 종료 성공/실패 프로세스 검사 및 위 7개 강제 종료·정상 닫기 시나리오가 통과했습니다. Intel은 컴파일 검증이며 실제 실행은 별도입니다.

반복 저장에서 불필요한 전체 원본 읽기를 줄이기 위해 기기·inode·크기·수정 시각·변경 시각을 먼저 확인합니다. 외부 변경 알림은 이 빠른 경로를 무효화하며, 파일 상태가 달라지면 내용 해시를 확인합니다. 변경이 감지됐는데 내용이 다르면 사본을 보존합니다.

M1 Pro / 16GB에서 2만 획·200만 좌표의 실제 비동기 저장을 3회 측정했을 때 전체 완료는 4.10–4.87초, 메인 응답 최대 간격은 31.54–39.28ms였습니다. 1만 획 측정에는 최대 74.22ms의 지연도 있었습니다. 이전 측정과 별도 실행이며 메모리 압력·다른 프로세스 부하를 통제한 A/B 시험이 아니므로 정확한 배수 개선이나 무지연을 주장하지 않습니다. [원본 수치](SAVE_BENCHMARK_RECOVERY.csv)를 보관합니다. 이 수치는 저장 경로의 5ms 타이머 응답 간격이며, 실제 필기 프레임·복구 기록을 쓰는 모든 편집의 지연을 측정한 것은 아닙니다.
