# 저장 성능 측정 (2026-11-01)

Apple M1 Pro, RAM 16GB, macOS 27.2, arm64 Swift 6 `-O` 빌드에서 실제 `NoteDocument.data(ofType:)` 및 `persistNow` 경로를 측정했습니다. 개인 노트와 설치된 앱은 변경하지 않았습니다. 결과 원본은 [SAVE_BENCHMARK.csv](SAVE_BENCHMARK.csv)입니다.

## 방법

`./scripts/benchmark-saving.sh`로 재현합니다. 별도 진단 실행 파일을 캐시에 빌드하고 임시 디렉터리의 합성 문서만 사용합니다. 각 획은 위치·시각·필압을 가진 좌표 100개이고, 문서 크기마다 3회 측정합니다. 5ms 주기의 메인 RunLoop 타이머에서 가장 긴 콜백 간격을 기록합니다. 이는 실제 마우스 입력 지연이나 프레임 시간의 직접 측정은 아닙니다. 이미지·캔버스 렌더링·iCloud 동기화 비용은 포함하지 않습니다.

- `main_encode`: 현재 문서의 검증 및 전체 JSON 인코딩.
- `main_safe_save`: 현재 `persistNow` → NSDocument 안전 저장 경로. 인코딩과 파일 쓰기 포함.
- `background_prototype`: 메인 액터에서 값 타입 스냅샷을 얻고 detached utility 작업에서 전체 JSON 인코딩 및 임시 파일의 atomic 쓰기. NSDocument 자동 저장에 연결한 구현은 아닙니다.

시제품 저장 완료 시간은 각각 약 156–158ms, 1,527–1,606ms, 7,454–15,564ms였습니다. 저장 총시간을 줄이는 효과와 UI 응답성을 유지하는 효과는 구분해야 합니다. 2만 획 결과는 반복 간 편차가 매우 커서 안정적인 속도 수치로 일반화할 수 없습니다. 메모리 압력·다른 프로세스 부하·스케줄링 원인은 분리 측정하지 않았습니다. 이 조건에서는 백그라운드 인코딩만으로도 모든 지연이 없어지지는 않습니다.

측정 중 프로세스 샘플에서 작업 스레드의 JSONEncoder 호출을 확인했습니다. 작업 프로세스 RSS는 한 시점에 약 1.7GB였습니다. 이는 최대 메모리 측정은 아니며 앱의 평상시 메모리 사용량을 의미하지 않습니다.

## 정합성 검사

각 크기에서 저장 스냅샷을 작업 스레드로 넘긴 뒤 메인 문서에 획을 추가했습니다. 이전 스냅샷은 바뀌지 않고, 추가 획이 현재 문서에 남으며, 뒤이은 현재 저장 경로로 저장·재독해 전체 데이터가 일치하는 것을 확인했습니다. 세 크기 모두 통과했습니다. 자동 저장 연속 요청·닫기·종료·외부 파일 충돌·쓰기 실패의 백그라운드 처리를 검증한 것은 아닙니다.

## 판단 및 다음 구현 범위

전체 문서를 메인 스레드에서 인코딩하는 현재 구조에는 체감 가능한 멈춤이 있으므로 개선이 필요합니다. 이번 변경은 **진단 도구와 측정 결과만 추가**하며 배포 앱의 저장 방식은 그대로입니다.

실제 적용 시에는 메인 액터의 불변 스냅샷, 문서별 순차 저장, 저장 중 새 편집의 dirty 상태 보존, 오래된 저장이 최신 파일을 덮어쓰지 않는 보장, 닫기·종료 시 마지막 저장 완료 대기, NSDocument 안전 저장 및 오류 처리의 유지가 필요합니다. 큰 문서는 이후 증분 저장 또는 이미지 별도 바이너리 저장도 검토할 대상입니다. 시제품의 atomic 쓰기를 그대로 자동 저장에 연결해서는 안 됩니다.
