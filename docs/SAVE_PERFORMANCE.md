# 저장 성능 측정 및 실제 적용 (2026-11-01)

Apple M1 Pro, RAM 16GB, macOS 27.2, arm64 Swift 6 `-O` 빌드에서 실제 `NoteDocument.data(ofType:)` 및 `persistNow` 경로를 측정했습니다. 개인 노트와 설치된 앱은 변경하지 않았습니다. 결과 원본은 [SAVE_BENCHMARK.csv](SAVE_BENCHMARK.csv)입니다.

## 이전 버전 측정 방법 (0.6.0)

`./scripts/benchmark-saving.sh`로 재현합니다. 별도 진단 실행 파일을 캐시에 빌드하고 임시 디렉터리의 합성 문서만 사용합니다. 각 획은 위치·시각·필압을 가진 좌표 100개이고, 문서 크기마다 3회 측정합니다. 5ms 주기의 메인 RunLoop 타이머에서 가장 긴 콜백 간격을 기록합니다. 이는 실제 마우스 입력 지연이나 프레임 시간의 직접 측정은 아닙니다. 이미지·캔버스 렌더링·iCloud 동기화 비용은 포함하지 않습니다.

- `main_encode`: 현재 문서의 검증 및 전체 JSON 인코딩.
- `main_safe_save`: 현재 `persistNow` → NSDocument 안전 저장 경로. 인코딩과 파일 쓰기 포함.
- `background_prototype`: 메인 액터에서 값 타입 스냅샷을 얻고 detached utility 작업에서 전체 JSON 인코딩 및 임시 파일의 atomic 쓰기. NSDocument 자동 저장에 연결한 구현은 아닙니다.

## 결과

| 획 / 좌표 수 | JSON 크기 | 현재 안전 저장 시간 | 현재 메인 응답 최대 간격 | 시제품 메인 응답 최대 간격 |
|---|---:|---:|---:|---:|
| 1천 / 10만 | 6.5MB | 159–169ms | 159–169ms | 5.44–5.62ms |
| 1만 / 100만 | 66.0MB | 1,525–1,620ms | 1,525–1,620ms | 5.54–5.63ms |
| 2만 / 200만 | 132.7MB | 3,208–15,246ms | 3,208–15,246ms | 138–207ms |

시제품 저장 완료 시간은 각각 약 156–158ms, 1,527–1,606ms, 7,454–15,564ms였습니다. 저장 총시간을 줄이는 효과와 UI 응답성을 유지하는 효과는 구분해야 합니다. 2만 획 결과는 반복 간 편차가 매우 커서 안정적인 속도 수치로 일반화할 수 없습니다. 메모리 압력·다른 프로세스 부하·스케줄링 원인은 분리 측정하지 않았습니다. 이 조건에서는 백그라운드 인코딩만으로도 모든 지연이 없어지지는 않습니다.

측정 중 프로세스 샘플에서 작업 스레드의 JSONEncoder 호출을 확인했습니다. 작업 프로세스 RSS는 한 시점에 약 1.7GB였습니다. 이는 최대 메모리 측정은 아니며 앱의 평상시 메모리 사용량을 의미하지 않습니다.

## 정합성 검사

각 크기에서 저장 스냅샷을 작업 스레드로 넘긴 뒤 메인 문서에 획을 추가했습니다. 이전 스냅샷은 바뀌지 않고, 추가 획이 현재 문서에 남으며, 뒤이은 현재 저장 경로로 저장·재독해 전체 데이터가 일치하는 것을 확인했습니다. 세 크기 모두 통과했습니다. 자동 저장 연속 요청·닫기·종료·외부 파일 충돌·쓰기 실패의 백그라운드 처리를 검증한 것은 아닙니다.

## 이전 측정의 판단

0.6.0의 전체 문서 메인 스레드 인코딩에는 체감 가능한 멈춤이 확인됐습니다. 최초 측정 커밋(18356ef)은 진단 도구와 결과만 추가했습니다. 이후 0.7.0에서 아래와 같이 실제 자동 저장에 적용했습니다.

실제 적용 시에는 메인 액터의 불변 스냅샷, 문서별 순차 저장, 저장 중 새 편집의 dirty 상태 보존, 오래된 저장이 최신 파일을 덮어쓰지 않는 보장, 닫기·종료 시 마지막 저장 완료 대기, NSDocument 안전 저장 및 오류 처리의 유지가 필요합니다. 큰 문서는 이후 증분 저장 또는 이미지 별도 바이너리 저장도 검토할 대상입니다. 시제품의 atomic 쓰기를 그대로 자동 저장에 연결해서는 안 됩니다.


## 실제 적용 (0.7.0)

NSDocument의 `canAsynchronouslyWrite`를 활성화하고, 편집 모델을 잠금으로 보호한 값 스냅샷을 작업 스레드에서 얻습니다. 이후 `unblockUserInteraction`을 인코딩 전에 호출하므로 전체 JSON 인코딩과 파일 쓰기 중에도 입력할 수 있습니다. 원본 모델은 메인 액터에서만 편집하고 스냅샷과는 Swift copy-on-write로 분리됩니다. 잠금을 인코딩 동안 유지하지 않고, 매 편집마다 문서 전체를 복제하는 영구 미러도 두지 않습니다. 백그라운드 저장 스레드에서 메인 큐로 동기 진입하면 AppKit의 상호작용 대기와 교착할 수 있으므로 그런 호출은 사용하지 않습니다.

파일 교체·파일 접근 직렬화·수정 시각·저장 변경 토큰은 NSDocument의 기본 구현을 유지합니다. 편집 모델의 변경은 명시적으로 추적하고 UndoManager의 그룹 알림은 중복 계수하지 않습니다. 자동 저장은 진행 중인 획을 끊지 않으며, 명시적 닫기·종료는 현재 입력을 마무리합니다. 종료·업데이트 재시작은 모든 문서를 저장하고, 대기 중 다른 문서에서 생긴 편집도 다시 검사해 저장합니다. 실패 시 종료를 취소하고 기존 파일과 미저장 편집을 유지합니다.

검증 결과:

- 잠시 멈춘 저장에 새 획 추가 및 기존 획 이동: 이전 스냅샷 불변, 새 편집 dirty 유지, 다음 저장의 전체 일치.
- 겹친 저장 요청: 이전 저장이 최신 내용을 덮어쓰지 않음.
- 저장 상태로 Undo, 다시 Redo: 변경 상태가 정확히 복원됨.
- 저장 중 창 닫기 요청: 최신 파일 저장 이후 닫기 허용.
- 두 문서의 종료 저장 중 먼저 저장한 문서 재편집: 다시 저장하여 모두 최신 상태로 완료.
- 인코딩/쓰기 오류 주입 및 실제 잘못된 경로 쓰기: 원본 파일·dirty 상태 보존, 재시도 성공.
- 실제 AppKit 자동 저장 타이머 작동 확인.
- 별도 프로세스의 실제 NSApplication 종료: 진행 중 자동 저장 이후 최신 입력까지 저장하고 정상 종료.
- 별도 프로세스의 종료 쓰기 실패: 종료 취소 및 메모리 편집·기존 파일 보존.
- 기존 네이티브 필기·이미지·도형 회귀 검사와 코어 테스트 15개 통과.

실제 전원 차단·강제 종료, iCloud/네트워크 볼륨의 외부 충돌 복구, Sparkle의 실제 설치까지 검증한 것은 아닙니다. 파일 전체 JSON 인코딩 비용과 메모리 사용량을 줄이는 증분 저장은 후속 과제입니다.

참고: [Apple 비동기 쓰기](https://developer.apple.com/documentation/appkit/nsdocument/canasynchronouslywrite(to:oftype:for:)), [입력 재개 시점](https://developer.apple.com/documentation/appkit/nsdocument/unblockuserinteraction()).


## 적용 후 성능 (0.7.0 universal 배포판의 arm64 실행)

같은 M1 Pro / 16GB에서 `--save-benchmark --save-benchmark-applied --self-test`로 실제 `persistLatest` → AppKit 비동기 안전 저장을 크기별 3회 측정했습니다. 첫 회에는 비어 있지 않은 새 문서의 파일 경로 배정도 포함합니다. 모든 경로를 임시 디렉터리에 제한하고 테스트 종료 후 삭제합니다. [적용 후 원본 수치](SAVE_BENCHMARK_APPLIED.csv)를 함께 보관합니다.

| 획 / 좌표 수 | 저장 전체 완료 시간 | 메인 응답 최대 간격 (각 회 범위) |
|---|---:|---:|
| 1천 / 10만 | 164–178ms | 11.65–14.16ms |
| 1만 / 100만 | 1,596–1,684ms | 9.90–14.06ms |
| 2만 / 200만 | 3,088–3,292ms | 11.37–15.22ms |

동일한 5ms 타이머 기준에서 이전 메인 스레드 저장의 최대 간격(1만 획 1.53–1.62초, 2만 획 3.21–15.25초)보다 응답 지연이 줄었습니다. 저장 총시간 자체는 여전히 문서 크기에 비례합니다. 이전 2만 획 측정의 큰 반복 편차는 원인이 분리되지 않았으므로 정확한 배수 개선으로 일반화하지 않습니다. 실제 필기 중 프레임 시간·Sidecar 하드웨어 지연·최대 메모리 사용량을 측정한 결과는 아닙니다.

추가 측정에서 아직 파일이 없는 문서의 첫 저장이 동기 초기화 경로로 들어가는 문제를 발견해, 해당 경로도 비동기 `save(to:...)`로 바꿨습니다. 새 문서의 비어 있지 않은 첫 저장도 작업 스레드 인코딩 및 파일 내용 일치 검사를 통과했습니다.
